> 状态：设计稿（待评审）

## 0. 设计目标与验收指标

| 目标 | 现状（2.0） | 3.0 验收标准 |
|---|---|---|
| 回填成功率 | chapter_02 实测 4951/4953 行匹配失败 | 对内置样例集 100%；真实长文件 ≥99%，失败行有明确原因 |
| 人工介入 | Step5 需逐条修特征码/引号/英文 | 常规章节人工仅审校译文本身；结构错误 0 次 |
| 结构破坏 | 模型改特征码、漏引号、破坏 `{w}`/`[var]` | 标签/插值校验拦截率 100%（测试集内） |
| 易用性 | 6 步按钮 + 4 个目录，顺序错了会坏 | 单窗口状态机，任何时刻关闭重开可续；误操作不产生坏数据 |
| 端到端流程 | 手动跑 UnRen 反编译 → 手动复制 tl 文件 → 翻完手动放回游戏 | 选游戏目录一键完成：解包→反编译→导入→翻译→写回游戏 |
| 安全 | API Key 入库 | Key 只存于 gitignore 文件/环境变量；日志无 Key |

不追求的目标：多语言界面、非 Ren'Py 引擎支持、机器翻译离线模型。

## 1. 与现状的差异总览（为什么这样改）

| # | 2.0 现状做法 | 3.0 做法 | 解决的问题 |
|---|---|---|---|
| 1 | 让模型复述「定位符\|特征码\|台词」三列 | **模型只返回 `{行号, 译文}`**，结构数据永不离开程序 | 特征码被改/漏冒号/瞎编 md5、围栏、多余行、引号错位——审查中最大的失败源 |
| 2 | 特征码精确匹配回填 | **uid 主键回填** + 归一化/相似度两级兜底 + 熔断 | output.py 的 4951 条未匹配 |
| 3 | 靠 `-s.csv` 文件是否存在来断点续传 | `project.json` 显式状态 | 关闭重开、失败重译、部分重译都可控 |
| 4 | 每 30 行独立翻译 | 携带**前块末尾 2~3 行原文+译文**作为上下文 | 人称/称呼前后不一致 |
| 5 | 串行请求、无超时 | 3~5 线程并发 + `timeout` + 指数退避重试 | 速度与网络挂起卡死 |
| 6 | 「含英文」全部报人工 | 白名单**自动豁免** + 漏翻**闭环重译**直到无漏翻（§5.3） | 大量误报与漏翻全靠人工逐条校验 |
| 7 | 不校验 Ren'Py 标签 | 校验 `{tag}` / `[插值]` / `\n` 与原文计数一致 | 现在最致命却没查的错误类型 |
| 8 | 6 个脚本 + 2 个菜单壳 | 单体 `pytran` 包，GUI/CLI 共用同一引擎 | 三套坐标系、GBK/UTF8 混用、路径基准不一 |
| 9 | 提示词里写死上个游戏的人名表 | 每游戏 `profile`，自动抽取角色名 | 换游戏要手改 JSON、人名不统一 |
| 10 | 无解包能力，用户需自行运行 UnRen 并来回复制文件 | 内置 UnRen 全套功能（提取 RPA / 反编译 rpyc / 辅助补丁）+ **写回游戏目录** | 新手在第一步就卡住；导出后还要手动找目录放文件 |
| 11 | 无 tl 骨架生成能力，需用户自行用 Ren'Py SDK 手动生成 | 设置中配置 SDK 目录即可自动调用生成（§8.5）；未配置时回退内置骨架 | 反编译出的游戏没有 tl 文件时流程走不下去 |

## 2. 总体架构

### 2.1 模块划分

```
pytran/
├── config.py        # 配置 dataclass；读写 config.ini；API Key 优先取环境变量 TL_API_KEY；Ren'Py SDK 目录（§8.5）
├── models.py        # Segment / Project dataclass + 状态枚举
├── parser.py        # .rpy → Segment 列表；Segment 列表 → .rpy（往返一致）
├── segmenter.py     # 切块（按 uid 顺序、动态块大小、带上下文）
├── terms.py         # 术语表：从 rpy 自动抽取 Character("...") / old "..." 高频项
├── providers.py     # OpenAI 兼容客户端（官方 openai SDK，base_url 可换端点）
├── validators.py    # 全部校验规则与自动修复（见 §5）
├── engine.py        # 翻译编排：并发、重试、校验、状态流转
├── backfill.py      # 译文写回 Segment（uid 主键 + 兜底链，见 §6）
├── exporter.py      # 导出 .rpy；CSV 导入/导出（人工用表格编辑的通道）
├── unren.py         # 游戏解包/反编译/补丁注入/写回游戏目录（整合 UnRen，见 §8）
├── project.py       # project.json 的加载/保存/迁移导入（旧版数据）
├── ui.py            # Tkinter 单窗口状态机
└── cli.py           # 命令行入口（与 GUI 同一引擎，供高级用户/自动化）
vendor/
├── unrpyc/          # 反编译器（CensoredUsername/unrpyc，F95Sam 编辑版，源码内置）
└── rpatool/         # RPA 解包器（Shizmob/rpatool，源码内置）
tests/
├── fixtures/        # 各类 rpy 样例（正常块、old/new 块、转义引号、标签、空行变体…）
├── test_parser_roundtrip.py
├── test_protocol.py
├── test_backfill.py
├── test_unren.py
└── test_e2e_mock.py
```

### 2.2 工作目录布局

```
<工作目录>/
├── project.json      # 唯一状态文件（§3）
├── profile.json      # 本游戏术语表/提示词 profile（terms.py 生成骨架，UI 可编辑）
├── bak/              # 导入的原始 rpy、每次导出的副本、写回游戏前的游戏原文件备份

`csv/ split_csv/ csvbak/ rpybak/` 不再是流程必需；旧项目通过「迁移导入」进入 3.0（§10）。

## 3. 数据模型与状态文件

### 3.1 Segment（一行为一条）

```json
{
  "uid": 123,
  "file": "chapter_02.rpy",
  "locator": "# game/scripts/story/chapter_02.rpy:22",
  "feature": "translate chinese chapter_two_6901eeea:",
  "kind": "dialogue",            // dialogue=普通台词块 | strings=old/new 块
  "comment": "# \"I still had trouble believing my eyes.\"",
  "role": "",
  "source": "I still had trouble believing my eyes.",
  "target": null,
  "status": "pending",           // pending | translated | reviewed | failed | keep_declared(AI申报保留,待人工) | skipped
  "attempts": 0,
  "error": null,
  "indent": 4                    // 还原 rpy 时使用
}
```

要点：
- **uid 全局唯一、只增不减**，与切块无关——重切块、重排序都不会破坏对齐。这是对「行号错位」类问题的釜底抽薪。
- `feature` 降级为**校验信息**，不再是主键。
- `indent`、`kind`、`comment`、`role` 记录还原 rpy 所需的全部原貌信息，导出时从内存重建，**不再经过「五列 CSV 中转」这条会丢格式的路**。

### 3.2 project.json

```json
{
  "version": 3,
  "app": "pytran",
  "files": [{"name": "chapter_02.rpy", "sha256": "…", "imported_at": "…"}],
  "next_uid": 124,
  "segments": [ /* §3.1 */ ],
  "term_profile": "profile.json",
  "game_root": "E:/pgd505/…",     // 关联的游戏目录（§8），空表示纯文件模式
  "stats": {"pending": 0, "translated": 0, "reviewed": 0, "failed": 0}
}
```

- 每次状态变更即原子写入（写临时文件 + `os.replace`）。
- 「断点续传」= `status != pending` 的行自动跳过；「失败重译」= 只取 `status == failed` 的行。不再以文件存在与否推断进度。

## 4. 翻译协议（核心改动）

### 4.1 请求

每块请求 = system + user 两段。

**system（profile 可覆盖）**：

```
你是专业的游戏本地化译者。用户会给你若干行带编号的 Ren'Py 脚本文本，格式为「编号|文本」。
你必须只输出 JSON 行，每行一条：{"i": 编号, "t": "译文"}
规则：
1. 将每一行翻译成自然流畅的简体中文；输出条数与输入条数一致，编号一一对应；顺序可以乱，但不能多、不能少、不能合并。
2. 文本中的 Ren'Py 标签（如 {w}、{b}、{color=#fff}）和插值（如 [player_name]）原样保留，种类和数量不得增减；转义符（如 \n、\"）原样保留。
3. 译文使用中文标点；禁止输出英文双引号（需要时用「」或『』）。
4. 拟声词、语气词按角色个性保留；人名等术语严格按术语表；忠实原文，不省略、不加戏、不文白夹杂。
5. 除 JSON 行外不得输出任何内容：无代码块围栏、无解释、无空行。
```

**user**：

```
术语表：
Ian=伊恩
Lena=莉娜

前文参考（已翻译，仅供衔接，不要翻译）：
102|I still had trouble believing my eyes.
    → 我还是难以相信自己的眼睛。

请翻译以下 30 行：
1|And I was pretty sure she had seen me, too.
2|...
```

要点：
- 上下文取**前一块已成功的最后 2~3 行**（原文+译文对）；第一块没有上下文。免费小模型也放得下。
- 术语表放 system（稳定内容利于缓存计费），前文参考放 user（每块变化）。
- 参数：`temperature=0.2`、`top_p=0.9`、`timeout=120`，通过 openai SDK 发送；SDK 自带连接重试。不再手写 `thinking_budget`/`response_format` 等非标参数（端点不认就 4xx）。

### 4.2 响应解析（宽进严出，三层兜底）

```
1. 预处理：剥掉 ``` 围栏、按行拆分、丢空行。
2. 逐行解析，依次尝试：
   a. json.loads → 取 i / t（主路径；未知附加字段忽略，`k`/`r` 申报字段按 §5.4 处理）
   b. 正则 {"i":\s*(\d+),\s*"t":\s*"((?:[^"\\]|\\.)*)"}   （模型 JSON 转义不规范时）
   c. 正则 ^(\d+)\|(.+)$                                   （模型退化成「编号|文本」时）
3. 组装 {uid: 译文}，丢弃未请求的多余编号；缺编号记为缺失。
```

### 4.3 校验与重试（引擎流程）

```
对每块：
  发送 → 解析 → 校验(§5)
  ├─ 全部通过 → 写 Segment.target，status=translated
  ├─ 部分行失败 → 只把失败行组成新请求重发，附错误说明
  │     （"第 3 行包含英文双引号，请重新只输出该行的 JSON 行"）
  │     重试轮数见 §5.3（默认 3 轮，指数退避 2s/4s/8s）；429/5xx 同样退避
  └─ 仍失败 → 该行 status=failed，error=具体原因，继续下一块（不中断全局）
```

并发：`ThreadPoolExecutor(max_workers=3~5)`（config 可调），每块原子提交回 project.json；UI 通过 `queue` 接收进度事件。**任何线程不直接碰 Tkinter**。

## 5. 校验规则与自动修复

按「先自动修、修不了才算失败」的顺序执行：

| # | 检查 | 自动修复 | 修复不了 → 失败原因 |
|---|---|---|---|
| V1 | 编号缺失/多余/重复 | 多余丢弃 | `missing: uid=…` |
| V2 | 译文为空 | — | `empty` |
| V3 | 代码围栏、首尾空白 | 剥离 | — |
| V4 | 英文双引号 `"` | 交替替换为「」/『』（沿用现有 check-UI 算法） | 仍含 `"` → `quote` |
| V5 | 含英文字母 | **白名单豁免**（§5.1） | 剩余字母 → `english` |
| V6 | 标签/插值/转义计数 | — | `tags: {w} 原文2处译文1处` |
| V7 | 特征码一致性（兜底阶段用，见 §6） | — | `feature_mismatch`（仅告警级） |

### 5.1 英文白名单

视为合法英文的条件（满足其一）：
- 命中术语表 key（人名、专名）；
- 命中用户「豁免列表」（profile 里可编辑，如 `Stalkfap`）；
- 该英文片段同样出现在原文中且为整词（如 `[var]` 内部、`{w=0.5}` 参数——但这类本就被 V6 语境豁免）；
- 启发式：连续字母 ≤3 的缩写（`OK`、`HP`）可通过配置开关豁免。

### 5.2 标签/插值校验实现

```python
TAG_RE  = re.compile(r'\{[^}]*\}')        # {w} {b} {color=#fff} {/b} {w=0.5}
VAR_RE  = re.compile(r'\[[^\]]*\]')       # [player_name] [config.name!t]
ESC_RE  = re.compile(r'\\.')

def tags_ok(src: str, dst: str) -> bool:
    return (Counter(TAG_RE.findall(src)) == Counter(TAG_RE.findall(dst))
            and Counter(VAR_RE.findall(src)) == Counter(VAR_RE.findall(dst))
            and Counter(ESC_RE.findall(src)) == Counter(ESC_RE.findall(dst)))
```

计数相等（允许换位置）而非顺序相等，避免对「语序调整」误报；`.rstrip()` 只对 V3 使用，**绝不动译文正文空白**。

### 5.3 漏翻检测与闭环重译（终结 2.0 的「包含英文」人工大清单）

2.0 里漏翻靠人工在错误查看器逐条看；3.0 的判定与修复都自动化，且**终止由检测手段保证**：放行在检测层完成，队列里只有真漏翻；收敛由检测结论驱动，不靠盲试次数。

**检测器输出（每行四态判定）**：

| 判定 | 条件 | 去向 |
|---|---|---|
| PASS 放行 | 剔除放行项后**残余为空**：无残留英文；或残留英文全部命中豁免（术语表 / `profile.exempt_english` / 标签插值转义 / ≤3 字母缩写开关 / 与原文同位置同词）；或 target==source 但剔除豁免后无实词（纯标点/符号/拟声占位） | 翻译完成，**不入队列** |
| UNTRANSLATED | target == source 原样返回，且剔除豁免后仍有实词 | 入重译队列 |
| RESIDUAL | target 非空，剔除放行项后仍残留英文 | 入重译队列 |
| EMPTY | 空译文（V2） | 入重译队列 |

**放行判定的固定顺序**：先剥标签/插值/转义（本就是保留项）→ 词级白名单匹配（术语表优先于通用豁免）→ 计算残余 → 按残余下结论。**放行的粒度是词/短语，行的结论由残余决定**：整行合法英文 → PASS 不入队；混合行（专名+真漏翻）→ 仍入队，且重发请求中注明哪些词是保留项（"Ian 为人名，保留"），避免模型把保留项当成待翻内容。

**闭环流程（由检测驱动，每轮结束重跑检测器）**：

```
轮数 > 5（代码硬上限，config 不得超）→ 剩余行全部强制置 failed（原因=round_budget）——无条件执行，先于一切检测判定
队列为空 → 收敛，完成
队列非空，本轮有行状态变化（有行翻译成功或有行新失败）→ 继续下一轮，只重发失败行
队列非空，且队列状态哈希（失败行集合+各行译文）与上一轮相同
    → 判定模型定点（STUCK），按有限策略序列升级：
        第 1 次定点 → 重发并逐行附具体错误原因
        第 2 次定点 → 切换 fallback_model / 略升温（config 可选）
        第 3 次定点 → 剩余行全部置 failed（原因=model_fixed_point），进入 §6.5 人工通道
状态哈希在任意时刻与历史某轮重复 → 判定循环（CYCLE），同上直接收敛到 failed
```

**为什么必然终止（构造性论证，不依赖运气）**：
- 队列不变量：入队的每一行都是「剔除放行项后确有残余/未翻」的行——误报行（合法英文）在检测层就被消解，永远不会进入循环；
- 策略序列有限：正常 → 详细原因 → 备用模型，共 3 档；每轮要么队列缩小、要么触发定点升级，升级次数有上限；状态哈希重复即停，连「两个错误输出间摇摆」的振荡也被覆盖；
- 轮数硬上限（代码 5 轮，config 不得超）**保留为无条件终止线**：达到上限立即强制失败剩余行，即使定点/循环检测因故未触发也不会失控；正常情况下它很少触发（检测会先收敛），主要兜底策略升级自身振荡与极端情况；
- 因此循环必然收敛到 PASS / failed 两态，failed 行带具体原因与完整轮次记录入日志，可回放「模型为什么翻不动这句」。

**边界情形**：拟声词/感叹词行（`Hahhh...`、`...`）「保留原文」常是正确译文——检测器对「原文为单个感叹类 token」的行提供 profile 级开关（放行或降优先级入队）；未放行的进入定点升级流程，最终落在人工通道而不是死循环。

**跨会话学习（人工裁定沉淀为放行规则）**：人工在 §6.5 把某行裁定为「保留原文」时，一键把该残留短语加入 `profile.exempt_english`（短语级，而非整行）——同样的英文下次直接 PASS，不再入队。reviewed 状态的行不参与闭环。

### 5.4 AI 申报保留标记（与检测层互补的语义信号）

检测层做词法判定（客观、可测试），AI 做语义判定（理解「这句为什么不用翻」）。两者互补：申报信号加速收敛、提升路由精度，但**不替代检测层，也不构成终止依据**。

**注入时机**：申报选项**只在重试轮的小请求中注入**（"若某行确实无需翻译——人名/拟声词/原文即为有意保留的英文——请输出 `{"i":n,"t":"<原文>","k":1,"r":"一句话原因"}`"）。首轮提示词保持最简，保证弱模型的 JSONL 遵从率；重试请求只有几行，指令遵从更好。标记是 JSON 字段而非文本内魔法字符串，不破坏「除 JSON 行外不得输出任何内容」的规则。

**接受的四道护栏**：
1. **申报 ≠ 放行**：申报行置 `keep_declared`，进 §6.5 人工裁定队列（附模型给的原因），绝不自动 PASS——模型无法借标记「混过去」，偷懒收益被消除；
2. **一致性约束**：仅当 `t == source`（或空）时接受申报；标记了却改了文本 → 按 UNTRANSLATED 拒绝重译；
3. **标记归一化**：`k` 接受 `1/true/"keep"` 等已知变体；未知变体按普通文本处理（走正常校验），宁可多翻不可漏放；
4. **申报率异常闸**：单批申报率 > 15%（config 可调）→ 该批全部申报降级为 UNTRANSLATED 重译并告警（提示词或模型问题）。

**与学习闭环的衔接**：人工裁定「确实保留」→ 短语入 `profile.exempt_english` → 此后同类行在检测层直接 PASS，无需再问 AI；人工裁定「其实该翻」→ 该行重译，并记录该模型的误报供评估。

## 6. 回填与导出

### 6.1 主路径：uid 直写

3.0 中 rpy 的再生成为：

```
原 rpy 行结构（内存保留）+ Segment.target → 逐行重建
```

因为解析时记录了 `kind/indent/comment/role/locator/feature`，重建时**除台词行外逐字节保持原样**。不存在「从 CSV 拼回 rpy」的中间层，往返一致性由构造保证。（2.0 的五列 CSV 中转层在 3.0 中降级为可选的人工编辑通道，见 §6.4。）

### 6.2 译文来源的兜底链（仅当 target 不是本引擎产生时，如迁移导入、用户手改 CSV）

```
1. uid 精确匹配                       ——主键
2. 特征码归一化匹配：去首尾、''""→"、
   全角/半角冒号统一、压缩连续空白     ——容错旧数据
3. difflib.SequenceMatcher 相似度 ≥0.92
   且定位符相同                        ——最后兜底，命中后打 warning
```

### 6.3 导出熔断

导出前按文件统计：

```
未翻译行数 >0          → 阻止，列出 uid/行号
status=failed 行 >0    → 阻止
标签校验未过行 >0      → 阻止
匹配率（迁移导入场景）< 0.95 → 阻止并展示具体行
```

弹窗列出明细，用户可选择「仍要导出（未匹配行保留原文）」或「取消」。现有「输出 csv 全英文却静默成功」的事故由这道闸终结。

### 6.4 CSV 导入/导出（人工编辑通道）

- 导出：`uid|定位符|特征码|角色名|原文|译文` 六列，`|` 分隔 + csv 模块标准引号，表头带 uid。供习惯用 Notepad++/Excel 修译文的人。
- 导入：按 uid 匹配写回，走 §6.2 兜底链；不做整文件静默覆盖。

### 6.5 人工校对通道（任何阶段可进入，可反复）

原则：自动化产出不是终点，人工修改后必须能无损地重新进入流水线。

**入口**（三个，同一套数据）：
1. **UI 审校页**：任何时候可打开（包括导出/写回之后）；左侧筛选器支持「仅失败 / 仅含英文 / 仅含标签告警 / 随机抽查 N 行 / 按文件」，右侧原文-译文对照编辑；
2. **CSV 往返**：§6.4 导出 → Notepad++/Excel 修改 → 导入回填；
3. **单行重译**：对任意行可发起「重译此行」，可附临时指令（如"这句要更口语"）；术语表修改后可一键「重译受影响行」（source 命中该术语的所有行）。

**规则**：
- 人工接受一条译文 → status=reviewed，此后**自动重译不再覆盖**（唯一例外：用户显式点「重译此行」）；
- 裁定「保留原文」→ 残留英文短语一键加入 `profile.exempt_english`（§5.3 跨会话学习），同类行此后直接 PASS，不再进入重译队列；
- **批量全部接受**：审校页对当前筛选结果一键批量置 reviewed（含 `keep_declared` 行）；操作前将受影响行原状态快照入 journal，可一键撤销本次批量操作；筛选结果含 `keep_declared` 行时可勾选「同时将其保留短语加入豁免表」（默认关闭，防一次性短语污染豁免表）；批量操作全量记日志；
- 人工/导入的译文在接受前重新跑 V1–V6 校验，防手滑引入结构错误；
- 修改后重新「导出」即基于最新 target 重建 rpy；写回游戏是**新事务**（§15.2），游戏目录永远可回滚；
- 由此支持的工作流：全自动跑完 → 玩游戏记下不顺的句子 → 审校页筛选/搜索 → 修改 → 再次写回，循环任意次。

## 8. 游戏解包与反编译（整合 UnRen）

> 集成对象：UnRen-forall v9.4（Sam @ f95zone.to & Gideon）。其 bat 通过 base64+cab 在运行时释放 unrpyc / rpatool，并借用**游戏自带解释器**执行；3.0 将这些能力原生内置并与翻译流水线打通。

### 8.1 功能对照（UnRen 9 项 → 3.0）

| UnRen 原菜单 | 3.0 对应 | 实现方式 |
|---|---|---|
| 1 提取 RPA 包 | 解包 | 内置 `vendor/rpatool`（纯 Python） |
| 2 反编译 rpyc | 反编译 | 内置 `vendor/unrpyc`（去多进程编辑版），默认 `--init-offset` |
| 3 开控制台/开发者菜单 | 辅助补丁（可选） | 写入 `game/unren-console.rpy`（`config.developer=True`、`config.console=True`） |
| 4 快速存读档 F5/F9 | 辅助补丁（可选） | `game/unren-quick.rpy`，热键可在配置中改（原版写死 K_F5/K_F9） |
| 5 强制跳过未读文本 | 辅助补丁（可选） | `game/unren-skip.rpy`（skip_unseen / allow_skipping / fast_skipping，TAB、CTRL 快进） |
| 6 强制回滚（滚轮） | 辅助补丁（可选） | `game/unren-rollback.rpy`（rollback_enabled、上限 256、解除 block_rollback，滚轮/PAGEUP） |
| 7 混淆游戏反编译 | 反编译高级选项 | unrpyc `--try-harder` 参数 |
| 8 提取+反编译 | 组合动作 | ①→② 串行执行 |
| 9 全部 | 组合动作 | ①→②，补丁**默认不勾选**（见 8.4） |

四个补丁的注入内容以 3.0 源码内**模板字符串**保存（等价于 UnRen 中解码出的 `init 999 python:` 块），不再用 base64 隐藏；模板渲染后写入游戏目录。

### 8.2 与 UnRen bat 的实现差异

1. **工具内置，无需释放临时文件**：unrpyc / rpatool 以源码进 `vendor/`（保留原作者许可与版权头），去掉 base64+cab+PowerShell 解码链，也不再依赖 `expand.exe`。
2. **解释器探测移植**：把 UnRen 的游戏解释器探测逻辑封装为 `detect_game_python()`——按 `lib/py3-windows-*` → `lib/windows-*` → `lib/py2-windows-*` → `lib/windows-i686` 顺序探测，设置 `PYTHONHOME`/`PYTHONPATH` 后优先调用游戏自带 python（老游戏 unrpyc 需要 py2/对应版本）；探测失败回退 3.0 自带解释器，并在日志中说明可能不兼容。
3. **幂等与可卸载（UnRen 原版没有的能力）**：
   - 所有写入游戏的文件统一命名 `unren-*.rpy`，写入前检测已存在则询问（跳过/覆盖）；
   - UI/CLI 提供「移除辅助补丁」一键删除全部 `unren-*.rpy`；
   - 解包/反编译/写回都先备份目标到 `bak/game/…`（首次触碰时），任何一步可整体还原。
4. **结构检测前置**：`is_renpy_game(root)`（存在 `game/` 与 `renpy/`，UnRen 同款判定）不满足时，解包/写回功能置灰并给出明确提示，避免把翻译工具的目录误当游戏目录。

### 8.3 一键工作流（GUI 状态机第 0 步；CLI 同名子命令）

```
[选择游戏根目录]
  → is_renpy_game? → 否: 提示并退出流程
  → 扫描 game/*.rpa 与 game/**/*.rpyc
      有 → 建议执行「提取+反编译」（进度条，输出到原位置；可选 afterwards 删除 RPA，对应 UnRen -r 参数）
      无 → 跳过
  → 扫描 game/tl/**/*.rpy
      无 → 生成骨架：a) 已配置 Ren'Py SDK（§8.5）→ 调 SDK 生成官方 tl 骨架
                b) 未配置或调用失败 → 内置近似骨架（translate chinese 块，写入游戏前再次确认）
      有 → 列出文件清单（行数、已译比例）→ 勾选导入 → 进入正常翻译流程（§4）
[导出]（§6 完成校验后）
  → 若 project.json.game_root 非空：写回 game/tl/<lang>/ 对应相对路径
      写回前把游戏内原文件备份到 bak/game/<相对路径>
      并提示：对应 .rpyc 需删除或让 Ren'Py 重新编译，否则游戏仍读取旧编译产物
  → 同时在 output/ 留一份副本（与纯文件模式一致）
```

细节：
- 语言目录默认 `chinese`（config 可改）；导入时记录游戏内相对路径，写回按原路径映射；
- 反编译出的 rpy 与同名 rpyc 并存时，导入流程在清单中标注「来源：反编译」，写回时自动为这些文件加 `.rpyc` 清理动作（默认勾选，可取消）；
- 辅助补丁（控制台/快存/跳过/回滚）在游戏目录页以独立勾选区呈现，与翻译流程解耦，勾选后立即写入并日志告知热键。

### 8.4 边界与许可

- `vendor/` 内的 unrpyc / rpatool 保留原许可与作者署名（CensoredUsername/unrpyc、F95Sam 编辑版、Shizmob/rpatool）；
- 3.0 不内置任何游戏资源，只对用户本机游戏文件操作；
- 「开控制台 / 强制跳过 / 强制回滚」属于**修改游戏行为**的功能：默认不启用、不随「全部」自动执行、随时可一键移除；文档中明确它们与翻译无关，仅为调试/测试便利。

### 8.5 Ren'Py SDK 集成（tl 骨架生成）

**配置**：`config.renpy_sdk_dir`。UI「设置」页选择目录，即时校验并显示探测到的 SDK 版本；支持配置多个候选目录，按游戏引擎版本自动挑选。

**目录校验**：SDK 根目录存在 `renpy.exe` / `renpy.sh` / `renpy.py` 与 `launcher/` 即有效；否则标记无效并在 UI 提示。

**引擎版本匹配**：从游戏根目录 `lib/` 子目录名推断运行时（`py2-*` → SDK 7.x；`py3-*` → SDK 8.x），自动选用匹配的 SDK；无匹配候选 → 警告并回退内置骨架，**不硬调**（避免生成不兼容骨架）。

**调用方式**（按优先级）：
1. 所装 SDK 若提供无头生成入口（新版 launcher 支持 CLI 参数时）直接调用；
2. 否则用**桥接脚本**方案：向游戏临时写入 `game/_pytran_gentl.rpy`（其 `init python` 调用 `renpy.translation.generation.generate_translations(<语言>, …)`——与 launcher「生成空翻译」走同一官方代码路径），用 SDK 解释器以无界面方式启动游戏、执行完自动退出，随后删除该临时脚本并记 journal（§15.2）；
3. 任一步失败 → 回退内置近似骨架。

**产物与衔接**：生成物位于 `game/tl/<语言>/`，直接进入 §8.3 的导入清单；日志记录 SDK 版本、命令行与生成统计（语言、文件数）。

**回退提示**：内置骨架覆盖率低于阈值（§15.3）时，报告中建议「配置匹配版本的 SDK 以获得 100% 覆盖」。

fixtures 至少覆盖：普通 `translate chinese` 块、`old/new` strings 块、台词含转义引号 `\"`、含 `{w}`/`[var]`、单引号字符串、连续空行变体、角色名带空格、`nvl`/无角色名行；`test_unren` 另需一个合成的小型游戏目录树（空 game/renpy/lib 结构 + 1 个极小 RPA + 1 个手写 rpyc）。

## 14. 风险与对策

| 风险 | 对策 |
|---|---|
| 免费小模型不遵守 JSONL 输出 | §4.2 三层解析兜底 + 逐行重试喂错误示例；最坏退化到 `n\|text` 仍可解析 |
| rpy 方言长尾（解析漏行） | 解析器对「无法归类的块」原样保留并计入 skipped，**宁可不翻不可弄坏**；fixtures 持续扩充 |
| 端点参数差异 | 仅用 OpenAI 标准参数（model/messages/temperature/top_p/max_tokens/timeout），非标参数全部移除 |
| 上下文注入增加 token 成本 | 每块仅 2~3 行；config 可关 |
| 并发触发限流 | max_workers 可调 + 429 退避；默认 3 |
| 老游戏引擎版本反编译失败（unrpyc 不支持或需 py2 解释器） | 保留 `--try-harder` 与多解释器探测（§8.2）；失败时输出 unrpyc 原始报错，并在日志提示回退到 UnRen 原版 bat 兜底 |
| SDK 版本与游戏引擎不匹配 | 从游戏 `lib/` 目录名识别 py2/py3 → 自动选对应 SDK；无匹配则警告并回退内置骨架（§8.5） |
| 漏翻闭环不收敛（死循环烧 token） | 终止由检测保证（§5.3）：检测层放行合法英文 + 定点/循环状态哈希检测 + 有限策略序列；轮数硬上限仅为预算安全网 |
| 模型滥用申报标记「逃翻译」 | 标记仅在重试轮注入（§5.4）；申报必须 t==source；批次申报率超阈值降级重译并告警；申报行一律进人工裁定不自动放行 |
| 写回游戏后游戏读取旧 .rpyc | 写回流程强制执行 rpyc 清理/重编译提示（§8.3），并在 bak/game 保留原文件可还原 |
| 辅助补丁改变游戏行为引发用户困惑 | 默认不启用、独立勾选区、一键移除、写入与移除都记日志 |
| 全自动模式写回破坏游戏目录 | 事务化写回（§15.2）：先备份、记 journal、可整体还原；L2 必须显式 `--yes` |
| 批量自动翻译超预算烧 token | dry-run 成本估算 + `--budget-max` 中止（§15.3） |

## 15. 全流程自动化分级

全流程自动化可行——各环节本身都已程序化，取舍不在「能不能」，而在**失败时谁发现、破坏性操作谁授权、质量下限谁来兜**。为此 3.0 定义三档自动化级别：同一引擎，不同检查点密度。

### 15.1 三档模式

| 级别 | 人工检查点 | 适用场景 | 入口 |
|---|---|---|---|
| **L0 交互**（默认） | 导入清单选择、术语表确认、写回确认 | 单游戏精翻 | GUI 默认 |
| **L1 半自动** | 仅术语表一处（约 5 分钟） | 速度与质量的平衡点 | GUI「快速模式」；`cli auto --level 1` |
| **L2 全自动** | 零人工；危险步骤按配置默认策略执行 | 批量过夜跑多个游戏 | `cli auto --level 2 --yes`（必须显式授权） |

```
pytran auto <游戏目录> [--level 0|1|2] [--yes] [--budget-max N]
  → 探测游戏结构 → 解包 RPA → 反编译 rpyc → 生成/定位 tl 骨架
  → 抽取术语表（L2：一次 AI 调用预翻译人名）→ 翻译（并发+重试）
  → 校验+自动修复 → 导出 → 事务化写回 → 生成报告
```

### 15.2 事务化写回（自动化的安全前提）

```
1. 全部产物先落在 output/（staging），游戏目录不动
2. 写回 = 单个事务：
   a. 生成 manifest（源文件→备份路径→新文件）
   b. 游戏原文件复制到 bak/game/<时间戳>/
   c. 按 manifest 移入新文件；按配置删除同名 .rpyc
   d. journal.json 记录每笔变更（含撤销信息）
3. 任一步失败 → 立即停止并报告；「一键还原」按 journal 逆向回滚
```

RPA 删除、rpyc 删除、辅助补丁在 L2 下的默认策略均由 config 显式声明，未声明的动作不执行。

### 15.3 质量门与成本闸

- **校验通过率**：写回前统计 V1–V6 通过率，低于阈值（默认 99%）中止，报告按文件/原因分组；
- **骨架覆盖率**：内置骨架生成时报告未覆盖节点数，低于阈值（默认 95%）中止并提示改用 Ren'Py SDK 生成；
- **成本估算**：开始前 dry-run 统计段数×平均长度→估算 token，超过 `--budget-max` 直接拒绝启动；
- **冒烟验证（可选）**：写回后启动游戏 exe，等待并检查 `traceback.txt` 是否生成（Ren'Py 脚本错误会写该文件），作为「游戏能跑」的最低信号；
- **术语表预翻译（L2 专用）**：全部人名/高频词合成**一次** AI 调用生成译名并注入术语表——保证全游戏人名一致，错误也一致，写入报告供用户事后修正。

### 15.4 批处理模式

`pytran auto-batch <游戏目录们或父目录>`：每游戏独立 project 目录，逐个执行 L2 流程；输出汇总表（成功/部分/失败、回填率、token 消耗）；失败游戏隔离并给出原因，不影响后续游戏。

### 15.5 不能自动化的部分（明确边界）

1. **语义质量**——语气、双关、梗、OOC，校验器只能保证「不坏」，不能保证「好」；
2. **反编译长尾**——加密/魔改 rpyc、超老引擎版本，失败只能报告，不能硬造；
3. **骨架生成 100% 覆盖**——内置近似实现有长尾；检测到本机 Ren'Py SDK 时优先调用官方生成；
4. **「这个译文是否合适」的最终判断**——所以 L1 把术语表保留为唯一人工检查点：成本 5 分钟，收益覆盖全游戏人名。
