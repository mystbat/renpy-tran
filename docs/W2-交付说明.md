## 三、核心实现策略（已留痕）

- `# DECISION(§5.4 护栏4 分母)`：单批率分母取**本批实际返回且被请求的行数**（`kept_rows`），而非请求行数——测的是「模型对已产出内容的偷懒比例」，少返回（缺行）反而稀释率，等于奖励少答；缺行由 V1 单独处理，不重复惩罚。
- `# DECISION(§5.4 护栏4 双闸)`：申报只在重试轮**小请求**注入（几行），而 15% 阈值是按正常批（数十行）标定的——`<5` 行的批次任意一次申报都轻易越阈，会令申报机制失效。故设单批最小样本量 5：小批次不触发单批降级闸，只逐条计入项目级累计计数器（靠护栏 1/2 人工裁定把关）；系统性滥用（每批都申报一大半但每批都 <5 行）在单批口径逃得掉，却在累计口径被逮出。详见 ADR-0006。

## 四、偏差与决策（deviation notes）

1. **护栏 4 由单闸改为双闸（ADR-0006）**：前序断点说明为救「小批次误降级」临时引入了 `KEEP_DECLARE_RATE_MIN_ROWS = 8`，与用户裁决冲突（裁决要求单批下限 5、并加累计闸）。本交付**删除该常量**，改为 `KEEP_DECLARE_MIN_BATCH = 5` + `KEEP_DECLARE_CUM_MIN_ROWS = 20` + `KeepDeclareAccumulator`，完全按裁决实现。旧 `W2-断点说明.md` 第 12–16 行所述「待定」方案已作废。
2. **§5.4 护栏 4 阈值/下限不进 `config.py`**：`config.py` 为冻结契约，不得修改。裁决原文 `len(batch) >= config.keep_declare_min_batch` 的实现等价物是**模块常量** `KEEP_DECLARE_MIN_BATCH`（+ `KEEP_DECLARE_CUM_MIN_ROWS`）与 `parse_response(accumulator=...)` 入参；W3 引擎持有 `KeepDeclareAccumulator` 并逐次传入。`config.py` 中既有的 `keep_declare_rate_limit = 0.15` 仍作比例阈值使用，未改动。
3. **429 退避测试修正**：`test_provider_retries_on_429_with_backoff` 原断言 `[2.0, 4.0]` 是错的——原 fixture 仅 1 次失败 + 1 次成功，只睡一次（2.0）。已补为「两次 429 + 一次成功」，让 2s/4s 两次退避都被覆盖，断言改为 `[2.0, 4.0]`，与退避序列预期一致。
4. **分支命名**：仓库主干为 `master`（无 `main` 分支），故本文与提交信息中的 `main..task/W2` 实际以 `master..task/W2` 执行。
5. **未执行 git 取回/合并指令**：前序裁决附带了「checkout task/W2 后合并 main 的 ADR-0006 与新 config / pull task/T0 的 1e5fefc」等指令。经核对：仓库无 `main` 分支、无 `ADR-0006` 历史、无 commit `1e5fefc`、无 `task/T0` 分支，`config.py` 亦冻结。上述 git 操作均不存在或不适用，已按纪律**不碰冻结文件、不跨分支搬运**，双闸通过常量 + 入参实现。ADR-0006 由本任务在 W2 worktree 内新写。
