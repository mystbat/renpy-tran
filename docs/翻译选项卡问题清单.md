### A1. 设置对话框「保存」在「译名为空」分支必崩 —— `re` 未导入 ✅ 已修复

**现象**
在「⚙ 设置 → 术语表」中，只要表格里存在**原文非空、译名为空**的行，点「保存」立即抛 `NameError: name 're' is not defined`，对话框不关闭、任何设置都不落盘。

**代码定位**
`pytran/ui.py:648`

```python
def save():
    ...
    for row in range(table.rowCount()):
        ...
        if dst:
            terms_map[src] = dst
        elif re.search(r"[A-Za-z]", src):   # ← 648 行，re 无绑定
            exempt_add.append(src)
```

**根因**
`re` 在 `pytran/ui.py` 中**从未导入**。已做四重确认：

1. 全文 `import re` 出现次数 = **0**（模块级 / 类级 / 函数级均无）；
2. `import pytran.ui; hasattr(module, "re")` → `False`；
3. `re` 不是 builtin，模块级也无 `re = ...` 赋值；
4. **决定性复现**：把 `save()` 函数体（`ui.py:631-664`）原样抽出，仅 stub 其依赖的 Qt 对象后执行：

```
RESULT: NameError -> name 're' is not defined
```

**为什么测试全绿却没人发现**
- `_open_settings` 整体位于 `run()` 内，`run()` 标注 `# pragma: no cover`；
- `tests/test_ui_settings.py` 的 12 个用例全部只调用 `_apply_settings` / `_coerce_setting` / `_validate_sdk`，**没有任何测试调用 `_open_settings`**（grep 全 tests 目录 0 命中）；
- GUI 的 `save()` 也从不调用 `_apply_settings`（见 A3）——即测试覆盖的路径与 GUI 真实路径是两条。

**复现步骤**
1. `运行.bat` 启动 GUI；
2. 点「⚙ 设置」→ 切到「术语表」页；
3. 点「添加行」，在「原文」列填 `Stalkfap`，**「译名」列留空**；
4. 点「保存」→ 崩溃。

> 注意：W5b 任务书 §3.2 的示例表格里 `Stalkfap` 一行正是「译名留空 = 按原文保留」，即**按设计文档教用户的操作必崩**。
> 若每行都填了译名，`if dst:` 先命中，`elif re.search(...)` 不执行，则不崩——这解释了为何部分操作路径下"看起来正常"。

### A2. 新增的 3 个数值字段在设置里退化为字符串 ✅ 已修复

**现象**
在设置里改「请求超时秒」「重译轮上限」「前文参考行数」后，**当次会话**内这些值是字符串，可能导致翻译启动即崩或参数被静默传错。

**代码定位**
`pytran/ui.py:162-180`（`_coerce_setting`）与 `pytran/ui.py:192-194`（留空白名单）

`_coerce_setting` 的类型分支只覆盖：

| 字段 | 收敛类型 | 状态 |
|---|---|---|
| `max_tokens` / `max_workers` / `round_budget_cap` | `int` | ✅ |
| `temperature` / `top_p` | `float` | ✅ |
| `timeout` | — | ❌ 按字符串 |
| `max_retry_rounds` | — | ❌ 按字符串 |
| `context_lines` | — | ❌ 按字符串 |

而这 3 个字段在设置 Tab1（`ui.py:540-554`）里都存在（`44bbf65` 新增）。

**根因**
`44bbf65` 给对话框加了 8 个字段，但只扩了 `Config`/`segmenter`/`engine` 的接收侧，没同步 `_coerce_setting` 的类型表，`_apply_settings` 的「数值留空保留既有值」白名单也没扩。

**会造成什么**

第一层（直接崩）：
- `_coerce_setting("max_retry_rounds", "3")` → `"3"`；
- `Config.effective_max_retry_rounds()` 执行 `min("3", 5)` → `TypeError: '<' not supported between instances of 'str' and 'int'`；
- 留空白名单不含这 3 个字段 → 用户清空 `timeout` 会把超时写成空串。

第二层（被 `Config.load` 掩盖，重启后自愈）：
`pytran/config.py:135-146` 的 `_coerce_types()` 会在读盘时把字符串转回数字。因此：
- **当次会话**：`cfg.timeout == "120"`（str）、`cfg.context_lines == "3"`（str），分别传给 openai SDK 的 `timeout` 与 `Segmenter(context_lines=)`；
- **重启 GUI**：从 ini 重新 load，类型恢复正常。

净效果是「改完设置，这次翻译用着坏参数，重启就好」——最不易被发现的一类缺陷。

**复现步骤**
1. 设置 → 常规 → 把「请求超时秒」改成 `60`，「重译轮上限」改成 `2` → 保存；
2. **不重启**，直接回翻译页点「开始自动翻译」；
3. 观察是否报错 / 参数是否生效（预期：`max_retry_rounds` 触发 `TypeError`，或参数被静默传错）。

### A3. 设置保存绕过 `_apply_settings`，测试覆盖的是 GUI 不走的路 ✅ 已修复

**现象**
设置对话框的「保存」与 `tests/test_ui_settings.py` 验证的逻辑**不是同一套代码**。

**代码定位**
`pytran/ui.py:631-634`

```python
def save():
    for attr, e in entries.items():
        setattr(cfg, attr, e.text().strip())   # 全部按字符串 setattr
    cfg.save(self.work_dir)                    # 直接落盘
```

**根因**
`save()` 未调用 `_coerce_setting`，也未调用 `_apply_settings`（`ui.py:182-196`）。后果：
- 13 个字段（含 `max_tokens`、`temperature`）**全部以字符串**写入内存 `cfg` 再 `cfg.save()`；
- `Config.save` 走 `_INI_SECTION_MAP` 逐项 `str()` 写 ini，所以 **ini 文件内容看起来正常**、重启后也正常；
- 但当次会话的 `cfg` 对象里数值字段全是字符串（与 A2 叠加，A2 的三个字段 100% 中招）。

**待用户确认**
此项与你的"亲测没有问题"存在冲突，需要区分实测口径：
- 若验证的是「保存后 `config.ini` 内容正确」或「重启后行为正确」→ 确实无问题（ini 落盘路径不依赖内存类型）；
- 若验证的是「不重启、改完立刻影响下一次翻译」→ 理论上 `config.temperature` 是字符串 `"0.5"`，会原样进入 openai 请求参数。

|---|---|---|

#### N1. 成本估算虚高 2.4 倍

**实测数据**（100 段，其中 50 段已译）：

```
全部 100 段（含 50 已译）估算: 21450
仅 50 未译段估算:              9100
```

**根因**
`_estimate_tokens(None)`（`ui.py`）传整个 `self.project`，而
`cli.estimate_token_budget` 的口径是 `Σ(source 长度 + target 长度)`。
已译行的 `target` 被全额计入，但引擎根本不会重发它们——
`TranslationEngine._build_queue` 只收 PENDING / FAILED / KEEP_DECLARED。

**后果**
用户看到的预估值比真实消耗高 2 倍以上：
- 预算设不准（按虚高值设 → 永远不触发，闸门形同虚设）；
- 或被虚假的超限警告反复骚扰（`budget_warn` 红条常亮）。

这个数字的唯一用途就是帮用户做决策，虚高直接让它失去价值。

**修法**
估算只对待译行求和：`[s for s in segments if s.status in (PENDING, FAILED, KEEP_DECLARED)]`，
与 `_build_queue` 口径严格一致。已实测 GUI 的「待译 N 行」计数与 `_build_queue`
大小一致（各 52），说明筛选条件可以复用。

#### N2. 「全部导入」全取消勾选 = 导入全部

**代码定位**
`ui.py _selected_import_files`：

```python
return picked or self._get_discovered_rpy_files()
```

**根因**
`picked == []` 时，`[] or discovered` 求值为 `discovered`（全部）。

**影响面**
- 「导入勾选的脚本」（`_import_selected_rpy`）有显式空检查，会弹「请至少勾选一个」——**正常**；
- 「全部导入」（`_import_rpy`）走 `_selected_import_files`——**有 bug**。

而 `9ee271f` 第 ⑤ 项把「全部导入」改成走勾选树，目的正是「取消勾选即跳过」
（实现部分导入）。这个回退逻辑把该意图破坏掉了。

**修法**
`_selected_import_files` 增加 `strict` 参数：勾选树存在且用户主动取消过勾选时
返回空列表（由调用方提示「请至少勾选一个」），不再静默回退全部。
仅在**树尚未构建**（`_refresh_import_tree` 未跑过）时才回退 discovered。

#### N3. 解包 worker 直接改 state（§9 红线一致性）

**代码定位**
`ui.py _on_unpack` 的 `worker()` 内：

```python
self.state.goto(1)   # 后台线程直接写 UI 状态
```

W5d 已把翻译路径的 `state.goto(3)` 改成发 `goto_step` 事件由主线程消费
（问题清单 C3/C4），解包这条路径漏改，导致同一条红线两处不一致。

**修法**
同样改为 `self.on_event("goto_step", {"step": 1})`。

#### N4. 停止后无终态反馈

**现状**
- `engine.stop()` 只置 `_stop_requested = True`，无返回值、无事件；
- UI `_stop_translate` 自己打了「已请求停止翻译」日志；
- 真正停下时（`run()` 的 `while queue` 开头 break）只发 `log`「翻译已被用户停止」，
  进度条仍留着停止前的百分比，无「已停止」终态。

**影响**
用户无法区分「已排停，正在等当前 in-flight 块跑完」与「按钮没反应」。
长跑（十万级）时这种不确定性会让人反复点击。

**修法**
engine 在 break 前发 `translate_stopped` 事件（含已处理块数/剩余行数），
UI 收到后把进度文字改为「已停止：完成 X/Y，剩余 Z 行未译」。

#### N5. GUI 写回绕过 §6.3 熔断

**代码定位**
`ui.py _on_writeback`：

```python
self.deps.exporter.write_back_project(self.project, self.work_dir, journal)
```

**根因**
`write_back_project` 是 W5 的协议扩展方法，**不跑熔断**；
跑熔断的是 `export_rpy`（`ExporterImpl.export_rpy` → `evaluate_export_fuse`）。

**后果**
§6.3 的四项熔断（未译行 >0 / failed 行 >0 / 标签校验未过 / 匹配率 <0.95）
在 GUI 写回路径上完全失效。用户点完「事务化写回游戏目录」才发现
未译/失败行被写进游戏，只能靠 `bak/game/` 回滚。
CLI 侧（`cmd_game` → `export_rpy_forced`）虽也绕过，但 CLI 用户可自行判断。

**修法**
`_on_writeback` 先调 `evaluate_export_fuse` 做预览：
- 无阻止项 → 直接写回；
- 有阻止项 → 弹窗列出明细（按文件/原因分组），提供「仍要写回」与「取消」两个选项
  （对齐 §6.3 原文：「用户可选择仍要导出（未匹配行保留原文）或取消」）。

#### N6. 翻译页不可观测 §5.3 / §5.4 内部状态

**现状**
`engine` 已发的事件里，UI 只消费了 `progress` / `segment` / `log` / `round` / `chunk_done`：
- `round` 事件只显示「翻译第 N 轮……（待译 M 行）」；
- §5.3 定点升级（STUCK stage 1/2/3）、CYCLE、`round_budget` 硬上限；
- §5.4 累计申报率闸（`keep_declare_rate_exceeded` 降级）；
- §5.3 第 2 次定点升级切 `fallback_model`。

这些**全部只进日志面板**，翻译页无可见反馈。十万级长跑时用户盯着进度条，
无法知道「卡在第几轮、是否在重试同一批、是否已切备用模型、什么时候会强制失败」。

**修法**
翻译页加一个「运行状态」小标签（或并入 `translate_info`），显示：
当前轮次 / 队列行数 / 是否已切 fallback_model / 最近一次 STUCK/CYCLE 级别。
终止时（`model_fixed_point` / `round_budget`）在进度标签给出明确终态文字。

### R1. 缺少「试译 / 小规模测试」入口

**需求**
除了「开始自动翻译」（全量），还需要一个供用户测试或小规模试译的功能。

**设计意图（用户原话）**
> 「让用户用于测试或者小规模试译」——即先用极少量样本验证
> 「模型选择 / 提示词 / 术语表 / 参数」这套组合是否合适，再决定是否全量开跑。
> 避免十万段工程跑了几千行才发现风格不对或术语没生效，返工成本极高。

**当前缺口**
- 翻译页只有「开始自动翻译」（全量）与「重试失败项」（仅失败行）；
- 引擎支持 `only_uids`（`engine.run(only_uids=...)`），GUI 只用于重试失败行；
- §6.5 的「单行重译」「术语表修改后重译受影响行」也无入口。

**建议方案**
新增「试译 N 行」按钮：
- N 默认取一个块大小（`config.block_lines`，默认 30），可在对话框调整；
- 从未译行中取前 N 条（按 uid 升序，与切块顺序一致，保证带上下文）；
- 走 `engine.run(only_uids={前 N 条 uid})`；
- 完成后提示「试译完成，请到审校页检查译文质量；确认无误后再全量翻译」；
- **不自动跳页**（试译目的是让人去看结果，不是催他进入下一步）。

**验收要点**
- 试译只发 N 行，不碰其余未译行；
- 试译结果与全量翻译走同一校验链（V1-V6 / 检测器），不是简化版；
- 试译后可随时「开始自动翻译」（未译的剩余行自然进入队列）。

### R2. 缺少「已译内容」的即时反馈

**需求**
> 「用户应该能在界面上即时的，看到现在已经被翻译的内容的反馈情况。
> 以便确认现在的翻译正在如预期进行。」

**当前缺口**
翻译页只有一个进度条 + 一行文字（`完成 X/Y 失败 N`）。
已译内容本身在审校页（Page 3），用户必须**切页**才能看到译文——
而翻译过程中切页会打断对进度条的观察，两者不可兼得。

**设计意图**
「如预期进行」包含两层，都要在翻译页可见：
1. **量**：进度（已有，但见 C1 历史问题）、失败数、轮次；
2. **质**：**实际译了什么**——译文长什么样、术语是否生效、风格是否统一。
   只有看到真实译文，用户才能判断「是否如预期」。

**建议方案**
翻译页加一个「最新译文」预览面板（只读 `QTextEdit` 或 `QListWidget`）：
- 翻译过程中，每当 `segment` 事件到达，追加显示最近若干条：
  `[uid] 原文 → 译文`（原文截断、译文全文）；
- 支持暂停/恢复自动滚动（长跑时用户想定住某条细看）；
- 失败行用红色标注并附 `error` 原因；
- `keep_declared` 行标注「AI 申报保留」；
- 面板只读，不影响审校页的编辑游标（审校页 `_review_index` 是独立状态）。

**与审校页的边界**
- 本面板是**预览**，不是编辑入口——避免与审校页的游标/编辑态竞争；
- 「细看/修改」仍引导去审校页（面板条目可加「去审校页查看」按钮，跳到审校页并定位该 uid）；
- 若后续需要直接在翻译页编辑，再评估是否合并游标（那会引入 C7 类复杂度）。

**验收要点**
- 翻译过程中新译文**即时**出现（不等整轮结束）；
- 原文/译文对照清晰，术语生效情况可判断；
- 失败与申报保留行有区分标识；
- 面板不影响性能（十万级时只保留最近 N 条，如 200 条）。

## 第五轮（2026-10-21）：W5e 落地 + A7 复审确认成立

### A7 复审：原「撤回」结论错误，缺陷真实存在

总控复核补充 1 曾以「run() 内已有 `_stop_requested` 重置」为由**撤回** A7。
本轮实现 N4 时**证伪了该撤回理由**：

`engine.py` 原第 87 行：

```python
self._stop_requested = False   # ← 在 run() 内部
```

这行重置会**吞掉 run() 之前设置的 stop 请求**。

**触发路径**
1. 用户点「开始自动翻译」→ `_ensure_engine_ready()` 组装 deps（可能是全新引擎实例）；
2. 在 worker 线程真正开跑前的窗口期内，用户点了「■ 停止」→ `engine.stop()` 置 `_stop_requested = True`；
3. worker 开跑 → `run()` 执行到第 87 行 → 标志被重置为 `False`；
4. 整轮翻译照跑，用户的停止请求静默丢失。

**本轮修复**
* `_stop_requested` 改为在 `__init__` 初始化，`run()` 内**不再重置**；
* `run()` 的 `while queue` 开头检测到停止时发 `translate_stopped` 事件
  （含 `processed` / `remaining` / `round`），UI 据此显示明确终态：
  「已停止：本轮已发 X 行，剩余 Y 行未译」；
* 回归测试 `test_engine_emits_translate_stopped_on_stop` 用一个
  **永不返回的 provider**：若引擎没在开头 break，测试会挂住而非误过。
