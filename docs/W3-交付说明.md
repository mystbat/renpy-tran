## 三、核心实现策略（已留痕）

- `# DECISION(§5.3)`：状态机终止严格按设计文档分层，硬上限 `round > 5` 是**无条件优先**分支，
  先于「队列空/有变化/定点」任何判定——保证永不超 5 轮。
- `# DECISION(§5.3 STUCK)`：定点升级三档中，第 2 档「升温」无契约通道（`interfaces.Provider`
  仅暴露 `use_fallback_model`），故引擎在 `config.fallback_model` 非空时切 fallback 模型，否则
  仅记 `log` 事件说明「无 fallback 可切、升温 noop」。这是已知偏差（见第四节#2）。
- `# DECISION(§5.4)`：申报提示（keep_declare 注入）仅出现在重试轮（`round_no > 1`），首轮最简，
  与设计文档「首轮不注入申报提示」一致；降级模式进入后后续轮仍按 `allow_keep_declare` 透传。
- `# DECISION(§6.2)`：回填回退链**仅适用于非引擎产出的目标**（迁移/CSV 导入）；引擎正常产出的
  译文以 `uid` 主键直接写回 Segment，不进回退链（避免把可靠译文降级为回退值）。
- `# DECISION(ADR-0009)`：Provider 只回 `dict[int, str|KeepDeclared]`，引擎负责「请求键−返回键」
  的**缺失恢复**（缺 uid→`FAILED(reason="missing: uid=…")`）与 `KeepDeclared` 分发。

## 四、偏差与决策（deviation notes）

1. **`include_errors` 标志的下游消费缺失**：引擎在 STUCK 第 1 档置 `include_errors=True`
   （设计文档要求「逐行带上错误原因」），但当前引擎与 `on_event` 契约**没有**把逐行错误原因
   注入 `translate_batch` 入参的现成通道——错误原因已通过 `_fail` 写入 `Segment.error` 并经
   `on_event("segment", …)` 上报。该标志保留为意图声明，无强制副作用。属契约层缺口，留待
   总控在 `interfaces.Provider.translate_batch` 增加 `errors: dict` 入参时启用。
2. **「升温」无契约通道（已知 noop）**：§5.3 STUCK 第 2 档要求「raise temperature」，
   但 `interfaces.Provider.translate_batch` 仅暴露 `use_fallback_model`，无 `temperature` 入参。
   当前实现：切 `config.fallback_model`（非空时）或记 noop log。`temperature` 变更需改冻结契约，
   本任务不触碰，已记入交付说明。
3. **Provider 丢弃 `ParseResult` 元数据**：`interfaces.py` 契约只要求紧凑 dict，逐行解析细节
   不外露。引擎是唯一恢复点（缺失/申报还原），已立 **ADR-0009** 解释该契约意图。
4. **分支/主干**：仓库主干为 `master`（无 `main`）。提交落在 `task/W3` worktree 分支。
5. **未触碰冻结契约**：`config.py` 等 8 个 T0 文件零改动；所有 W3 需要的新语义（降级模式、累计闸）
   均通过引擎持有计数器 + 读既有 `config` 字段实现，不新增/改契约字段。
