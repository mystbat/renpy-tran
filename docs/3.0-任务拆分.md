# Ren'Py 汉化工具 3.0 开发任务拆分（多 AI 会话协作版）

> 配套文档：[3.0-重构设计文档.md](./3.0-重构设计文档.md)（唯一需求来源，下称「设计文档」）
> 协作模式：每个任务由**独立的 AI 会话**完成；会话之间不共享上下文，只通过**代码 + 本文档 + 设计文档**衔接。每个任务完成后由总控（审核者）审查、跑测试、合并。

---

## 0. 全局约定（每个会话必须遵守）

1. **唯一需求来源是设计文档**。本拆分文档只做边界划分；两文档冲突时以设计文档为准，并在交付说明中指出冲突。
2. **接口契约冻结**：所有任务基于 `T0` 产出的 `pytran/models.py`、`pytran/interfaces.py`、`pytran/config.py` 开发。**任何会话不得修改这三个文件**（类型不足以表达需求时，在交付说明中提出，由总控裁决后统一改动）。
3. **Python ≥3.10**；标准库优先；第三方依赖仅允许 `openai`、`pytest`（W4 可加 `pytest` fixture 自带的最小依赖）。禁止引入其它运行时依赖。
4. 代码风格：`pathlib.Path`、类型注解、`logging`（禁止 print）、UTF-8、模块级 docstring 说明职责与对应设计文档章节。
5. **Git 纪律（强制）**：
   - 每个会话开工第一件事：`git checkout -b task/<编号>`（如 `task/W2`）；**禁止在 main 上直接提交**；
   - 小步提交：每完成一个可测试的单元（如"实现 V1-V3 校验"）提交一次，提交信息格式 `task(W2): 实现 V1-V3 校验与自动修复 [设计§5]`——前缀 + 做了什么 + 对应设计章节；
   - 测试与实现同分支：提交顺序要求「先提交测试（红）→ 再提交实现（绿）」，commit 信息中注明；
   - 禁止 `git push --force`、禁止改写他人分支、禁止把 `config.ini`、`*.rpy`、游戏文件、`__pycache__` 提交进库（`.gitignore` 由 T0 提供）；
   - 会话结束（交付）前：`git log --oneline main..task/<编号>` 输出贴进交付说明，供总控审核。
6. **决策记录纪律（强制）**：实现中做出的每个**非显而易见的取舍**必须留痕，分级记录：
   - **架构级**（影响跨模块接口、数据格式、外部行为）：在 `docs/adr/` 新建 `ADR-<nnnn>-<标题>.md`（模板见该目录 README），随实现分支一起提交；例：检测器四态判定的残余粒度、申报标记的护栏策略；
   - **任务级**（只影响本模块内部实现）：写入交付说明的「偏差与决策」小节，并在代码中以注释标注 `# DECISION(§5.3): …`；
   - 会话认为需要修改设计文档本身时：**不直接改**，在交付说明中提出「设计变更建议」，由总控评审后统一改文档并记 ADR。
7. **禁止越界**：只创建/修改「交付物清单」中列出的文件与对应测试文件；不碰其它任务负责的模块（需要用到时 `from pytran.interfaces import …` 引用契约中的 Protocol/签名，允许对未完成模块写临时 stub 于 `tests/` 内，禁止提交进 `pytran/`）。
8. 每个任务交付时必须附带：`python -m pytest <本任务测试文件> -q` 的通过输出、文件清单、对设计文档章节的覆盖对照表、`git log --oneline main..task/<编号>`、以及「实现与设计的偏差说明」（无偏差也要写明"无"）。
7. Git：每任务一个分支 `task/<编号>`，提交信息前缀 `task(W?)`。

## 2. T0 接口契约冻结（总控亲自完成，或单个小会话完成）

**目标**：让所有后续会话有一份稳定、自洽的类型与签名依据。

**交付物**：
- `pyproject.toml`（项目元数据 + 依赖声明 + pytest 配置）
- `pytran/models.py`：`Segment`（设计文档 §3.1 全部字段）、`SegmentStatus` 枚举（含 `keep_declared`）、`Project`、`stats` 结构
- `pytran/config.py`：`Config` dataclass（API/url/key/模型参数/并发/预算/`renpy_sdk_dir`/`fallback_model`/语言/`exempt_english` 引用等）+ ini 读写 + 环境变量 `TL_API_KEY` 优先
- `pytran/interfaces.py`：全部跨模块 Protocol——`Parser`、`Validator`、`Provider`（`translate(batch) -> dict[uid,str|KeepDeclared]`）、`Engine`（事件回调签名）、`Unren`、`Exporter`、`ProjectStore`；异常层级 `PytranError` 及子类
- `tests/conftest.py` 空骨架 + `pytran/__init__.py`

**验收**：`python -m pytest -q` 可运行（0 tests）；设计文档 §3 的每个字段在 models 中有对应且注释引用章节号。

## 5. 总控审核流程（每个任务完成后执行）

1. **契约一致性**：diff 是否触碰冻结文件；新增公开 API 是否与 `interfaces.py` 一致。
2. **设计符合性**：对照任务条目「设计依据」逐节检查（重点：W2 的检测顺序与豁免粒度、W3 的终止三层机制、W4 的备份/journal/许可保留、W5 的主线程约束与 L2 授权）。
3. **测试质量**：在本机跑验收命令 + 全量 `pytest`；审查测试是否覆盖边界（空文件、BOM、GBK 混入、超长行、CRLF）；拒绝恒真/快照式测试。
4. **Git 纪律**：分支名与提交信息格式合规；提交粒度合理（先测试后实现）；无越界文件、无 `.gitignore` 违禁品混入；`git log` 与交付说明一致。
5. **决策留痕**：架构级取舍是否已记 ADR 并提交；任务级取舍是否在交付说明与代码注释（`# DECISION(§…)`）中可追溯。
6. **安全检查**：grep key/Authorization/headers 是否可能入日志；打包配置是否可能带入真实 config.ini。
7. **集成冒烟**：每合并一个任务，跑一次「fixture 全链路」（mock provider）；W4 合并后加跑 `fake_game` 解包反编译；W5 合并后跑真实游戏目录演练（仅 dry-run）。
8. 不通过 → 退回原会话继续（把审核意见与 diff 一并发回），通过 → 合并主干并更新本文档状态表与 ADR 索引。
