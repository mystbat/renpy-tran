## 1. 这个 bug 的形态：它从不以「报错」出现

这是理解全部困难的前提。错位 bug 的每一次发作都长这样：

```
合并导入完成：新解析 666 段，按 uid 对位回填 646 行、兜底命中 0 行、0 行旧译文未匹配
写回成功：15 个文件
```

日志完美，数量完美，零异常，零失败。**唯一的症状在用户眼睛里**：
「这句话的译文不是我翻的。」

由此产生三个致命后果：

1. **自动化测试抓不到**。只要断言 `len(matches) == 646`，任何错位都能通过。
2. **熔断机制拦不住**。写回前熔断只查「未翻译/失败/标签不符/匹配率」，错位译文本身标签合法、长度合法、语法合法。
3. **修复无法验证**。修完之后日志还是那么漂亮，没人能证明问题消失了。

> **第一次认知转折**：验收标准必须从「匹配了多少条」改成「译文落在哪一段」。
> 这条转变直到第六轮才真正贯彻。

## 2. 六轮修复的演进

### 轮次总览

| 轮 | 提交 | 修复的键 | 声称的根因 | 被什么打破 |
|---|---|---|---|---|
| 1 | `ee3bed9` | uid 唯一性 | 解析器按文件局部计数，uid 撞车 | uid 重编导致跨导入不稳 |
| 2 | `744e4c2` | locator 文件名 | regenerate 用错文件名 | 与错位无关（顺带修复） |
| 3 | `ab69650` | **禁用** uid 匹配 | uid 跨导入毫无语义 | 用户裁决「根因不是匹配逻辑」 |
| 4 | `b13ce9e` | **重启用** uid + 稳定化 | uid 每次从 1 重编 | `path_hash` 只有 16 bit 会碰撞 |
| 5 | `064e3e1` | 提示词编号 | 前文参考区编号与 uid 撞车 | 只解决模型侧，不解决回填侧 |
| 6 | `0ae4ead`+本轮 | uid 校验文件 + 原文 | 特征码无文件边界 | 短原文相似度恰好 0.80 |

### 2.1 第一轮 `ee3bed9`：uid 撞车（跨文件）

**症状**：用户实测 10 文件 1468 段，只有 **436 个唯一 uid**（372 组重复）。

**根因**：`parser._emit` 按文件局部计数，每个 `parse_file` 的段都从 1 开始。

**后果**：uid 是引擎 `seg_map`、预览回查、审校游标的全局主键。`seg_map` 只剩每个 uid 的最后一条（其它文件翻译结果丢失）；预览 `_on_segment_event` 按 uid 回查取到第一条匹配 —— 跨文件张冠李戴，例如 `rpg.rpy` 的战斗文案显示了 `loca_screen.rpy` 的「划船返回大陆」。

**修复**：`build_project` 在组装 Project 前按传入顺序统一重编 uid 为 `1..N`。

**这一轮埋下的雷**：`1..N` 是**单次导入内**的序号。它让「本次导入内 uid 唯一」成立，但完全不保证「跨导入 uid 稳定」。而合并导入恰恰是跨导入操作。

> 这是整条歧路的起点：**修复了 uid 的唯一性，却让 uid 变成了一个每次导入都会变的量。**

### 2.2 第二轮 `744e4c2`：locator 文件名

`regenerate(project, file_name)` 内部生成 locator 时用的是 `self._file`（最后解析的文件），而非参数 `file_name`。多文件场景下 `line_for` 按 `file_name` 正确过滤了段，但键生成用错文件名 → 查不到 → 除最后解析的文件外全部原样输出，**译文静默丢失**。

这是真实缺陷，但与错位主线无关（它导致丢失，不是错位）。记录在此以保持时间线完整。

### 2.3 第三轮 `ab69650`：禁用 uid 匹配

**事故**：合并导回后写回，**15 个文件译文全部张冠李戴**（`common` 第 0 对 `new` 变成别处译文；`exp-wos` 2322 对错位）。用户游戏文件已从事发前快照逐字节恢复。

**根因判断（当时）**：`_merge_import` 走 `match_translations`，第一级是 uid 精确。uid 是「单次导入内的段序号」，跨导入毫无语义 —— 旧 `uid=5` 的译文命中新 `uid=5`（完全不同的另一段）并置 `REVIEWED`。特征码/相似度两级本是正确主键，却被 uid 级抢先命中。

**修复**：
- `match_translations` 新增 `use_uid_matching` 参数，**默认 `False`** —— 跨导入禁用 uid 级
- `_merge_import` 增加 `(文件, 原文)` 精确对位前置层

**这个判断其实是对的。** uid 在当时确实没有跨导入语义。

### 2.4 第四轮 `b13ce9e`：重启用 uid 并「稳定化」

**用户裁决**（记录在提交标题里）：
> 合并导入事故根因是 uid 每次从 1 重编，**不是匹配逻辑**

于是方案反过来：不动 uid 的主键地位，改 uid 的分配方式。

**新设计**：
```
uid = (blake2b(文件相对路径, digest_size=2) & 0xFFFF) << 16 | (文件内序号 & 0xFFFF)
```

**提交中写下的关键论断**：
> 同文件同段跨导入 uid 一致；**不同文件 hash 不同永不撞车**（多文件导入天然唯一）

**这句话是错的。** 而且它错得很隐蔽：`digest_size=2` 只有 16 bit，按生日问题，3000 个文件的期望碰撞数约 `3000²/2¹⁷ ≈ 68`。

**实测**（本轮验证）：3000 个路径 → **2941 个唯一 hash，59 次碰撞**，与理论期望 68 同量级。可复现样例：

```
tl/chinese2/file_1.rpy    → hash 17245
tl/chinese2/file_1710.rpy → hash 17245
两者 seq=1 的 uid 都是 1130168321

tl/chinese2/file_56.rpy   → hash 40439
tl/chinese2/file_228.rpy  → hash 40439
```

本轮同时把 `use_uid_matching` 默认改回 `True`。

> **这是整条线上最关键的一次转折。** 第三轮刚刚用血的代价证明了「uid 不可信」，
> 第四轮用一个**未经验证的数学假设**（16 bit 不会碰撞）把 uid 重新扶上主键地位，
> 并且把这个假设写进了代码注释和交付文档。之后所有轮次都在这个错误地基上盖楼。

### 2.5 第五轮 `064e3e1`：提示词编号撞车

**症状**：写回后重导新文件翻译，预览错位。

**根因**：`segmenter` 产出 2 元组 context，`provider._normalize_context` 按位置补号 `0,1,2...`，`build_user_prompt` 把这个编号当 uid 展示。首次导入 uid 是大数字不撞车；**写回后重导新文件时 `build_project` 把 uid 重编为 `1..N`**，与 context 位置编号大面积重叠 —— 同一编号跨「前文参考」与「待翻译」两区重复出现，模型输出的 `i` 指错行 → 译文错位。

**修复**：context 行改为引号包裹的纯文本，不带数字编号。

**注意这里的时间线咬合**：这个 bug 的成因直接引用了第一轮的 `1..N` 重编。**第一轮的修复在第五轮以另一种形式复发了。**

### 2.6 第六轮（本轮）：三个并行缺陷

用户报告两个新症状：

- **#5**：待翻译里有 `old "Take me to the Sylphir Island"`，翻译写回后变成 `new "{image=it_qu.webp} 波泽拉的水晶球"`
- **#6**：人工数有 20 个待翻译，审校界面只看到 19 个

**#5/#6 是同一个根因**，且**与 uid 完全无关**：

`strings` 类段落整块共用一个常量特征码 `translate chinese2 strings:`。`match_translations` 第二级用 `feat_index: dict[str, list[Segment]]` 建**全局**索引，15 个文件的 strings 段全部塌进同一个 list。`take()` 按 FIFO 派发 → `dlc.rpy` 的 27 条译文按顺序写进了 `exp-1-3somes.rpy` 的 27 个 strings 段。

**数值证明**（用未污染的写回前文件重解析）：

| 项 | 值 |
|---|---|
| 总段数 | 666（`dialogue: 638` + `strings: 28`） |
| 状态分布 | `{TRANSLATED: 646, PENDING: 20}` |
| 20 条 PENDING 构成 | **19 条 dialogue**（`:15311`…`:15419`）+ **1 条 strings**（`:15425`，`Take me to the Sylphir Island`） |

那 20 条正是用户手工数出的 20。第 20 条被塞入错误译文后状态翻成 `REVIEWED`，审校界面就只剩 **19** —— **#6 的「19 vs 20」由此而来，与 #5 同源。**

本轮实际修了**四个**并行缺陷：

| 缺陷 | 修复 |
|---|---|
| 特征码级无文件边界（#5 #6 主因） | `feature_candidates` 按文件收敛，取不到就返回 `None`，绝不跨文件借候选 |
| uid 碰撞跨文件覆盖 | `take_uid` 增加 `_same_file` 校验 |
| uid 漂移同文件错位 | `take_uid` 增加 `_same_source` 校验 + 相似度下限 |
| CSV uid 通道盲写 | `import_csv` 增加 `_same_source` 校验 |

## 3. 一个必须承认的事实：本轮测试又发现了两个新缺陷

这是复盘中最有价值的部分 —— 说明「修复后验证」本身也不可靠。

### 3.1 `SequenceMatcher` 在短串上撒谎

为容纳「原文被人工微调过」的场景，我设了相似度下限 `UID_SIMILARITY_FLOOR = 0.80`。测试场景 D（删除一行）立刻打穿：

```
删除前: 1=LINE1  2=LINE2  3=LINE3  4=LINE4  5=LINE5
删除后: 1=LINE1  2=LINE3  3=LINE4  4=LINE5
```

`SequenceMatcher(None, "LINE2", "LINE3").ratio()` **恰好等于 0.80** —— 正好卡在下限上，放行。`LINE2` 的译文落到了 `LINE3` 上。

**修复**：新增 `UID_SIMILARITY_MIN_LEN = 12`，短于该长度必须精确相等。理由：短句改一两个字符就是另一句话，而相似度算法在短串上极不灵敏。

### 3.2 我自己写下的「兼容性兜底」直接制造错位

特征码级原本有一层兜底：

```python
# 没有原文等值的 → 按位置取第一个，但这是「猜测」，必须留痕
s = free[0]
logger.warning("特征码级按位置兜底（原文不等）...")
```

理由是「改了一个标点就全部判未匹配会丢人工成果」。测试场景 D 证明它**连续制造三条错位**：

```
LINE2 的译文 → LINE3
LINE3 的译文 → LINE4
LINE4 的译文 → LINE5
```

**修复**：整个兜底删除。原文对不上就是不匹配，宁可留给人工审校，也不能猜。

> **这一条最值得记下来**：这层兜底是「为了兼容性」加的，加了日志、加了 warning、
> 加了 `on_warning` 回调 —— 我做了所有「负责任」的动作，但**它本身就是错位工厂**。
> 「有日志的猜测」仍然是猜测。

### 3.3 CSV 通道完全裸奔

`import_csv` 的 uid 分支：

```python
for uid in set(incoming) & set(by_uid):
    seg.target = incoming[uid]["target"]   # ← 完全不看原文
```

CSV 里的 uid 是**导出时**的快照。源文件之后增删行，uid 已漂移，盲写就是整体错一位。测试抓到：插入一行后导入旧 CSV 得到 `{'INSERTED': '猫', 'Cat': '狗', 'Dog': None}`。

**这说明前三轮的修复全部集中在 `match_translations` 一条路径上，而 CSV 是另一条完全独立的入口。** 同一类缺陷在两条路径上各存在一遍。

## 4. 五个反复踩的思维陷阱

这一节是本次复盘的真正产出。

### 陷阱一：把「数量正确」当成「结果正确」

六轮修复的验证都用了 `len(matches)`、`unmatched == 0`、日志里的「回填 N 行」。而错位 bug 的定义就是「数量正确、内容错误」。

**唯一的正确验收标准**：断言 `m.segment.source == m.row.source` 且 `m.segment.file == locator_file(m.row.locator)`。

老用例 `test_same_source_different_file_no_cross_match` 只断言 `len(out.matches) == 1` —— 它**在 bug 存在时一直是绿的**。

### 陷阱二：用一个「看起来更可靠」的键替换旧键，而不验证新键的可靠性

| 轮次 | 认为可靠的键 | 实际 |
|---|---|---|
| 1 | uid 唯一（本次导入内） | 跨导入不稳 |
| 3 | 特征码 + 相似度 | 特征码跨文件不唯一 |
| 4 | 文件路径 hash | 16 bit 会碰撞 |
| 6 | uid + 原文 | 短原文相似度不可靠 |

每一轮都是「这次换了个更硬的主键」。但**没有任何一轮先做了「这个键的碰撞率/歧义率是多少」的量化**。第四轮如果先跑一次 3000 路径的 hash 分布，就会立刻发现 **59 次碰撞**，`b13ce9e` 的整个设计前提就不成立。

**教训**：引入一个「唯一标识」之前，先测量它的碰撞率。这是可以一行代码做完的事。

### 陷阱三：为了让旧用例通过而迁就旧语义

本轮有 4 个老用例因为新的严格校验而失败：

- `test_match_by_uid_exact`
- `test_match_uid_takes_precedence_over_feature`
- `test_uid_match_wins_over_feature_and_is_cross_file_safe`
- `test_uid_matching_enabled_by_default`

一开始我的反应是放宽校验（先加了 0.80 宽容档）。但仔细看数据：这些用例写的是「uid=10 的段原文是 `hello`，而行原文是 `'x'` 或 `'world'`」，**用例自身数据就是矛盾的**，它们编码的正是「uid 盲胜」这个已证伪的语义。

同样地，`tests/test_ui_import_safety.py` 的夹具里旧段 `source="src 1"`、新解析出 `"source line for pytran import-safety test."`，两者完全不同却期望「同 feature 即继承」。

**正确做法**：判断是「代码错了」还是「用例编码了错误语义」。判据是**真实数据**。我查了 bak 里的 12099 段工程：**116 个 feature 组中有 30 组内部原文互不相同**，证明 feature 级必须比较原文，用例是错的。

**教训**：用例失败时，第一反应不能是「放宽代码」，而要问「这个用例断言的是真实业务语义，还是历史 bug 的快照」。

### 陷阱四：在错误的地基上持续加固

第四轮 `b13ce9e` 的「不同文件 hash 不同永不撞车」是一个**未验证的数学断言**。它被写进：

- `uids.py` 模块文档
- `project.py` 文档字符串
- 交付文档 `docs/BUGFIX-merge-uid-collision.md`

之后第五轮、第六轮的所有设计都建立在「uid 可信」之上。第六轮必须同时加 `_same_file` 和 `_same_source` 两道校验，本质上就是在**给第四轮的错误前提打补丁**。

**教训**：一个断言被写进文档后，就获得了「已被验证」的假象。文档里每一个「永不」「必然」「天然唯一」都是技术债的利息。

### 陷阱五：只修报告出来的那条路径

CSV 导入和合并导入是两条独立入口，共用同一套脆弱假设。前五轮全部只盯 `_merge_import → match_translations`，CSV 通道直到第六轮写测试才被发现完全裸奔。

**教训**：修一个匹配类缺陷时，先枚举**所有**消费该匹配逻辑的入口。

## 6. 现在的防护体系

### 6.1 四道校验

```
匹配请求
  │
  ├─ 第 1 级 uid
  │    ├─ _same_file  : locator 里的文件 == seg.file ?   ← 防 path_hash 碰撞
  │    └─ _same_source: 原文精确相等，或（长度≥12 且相似度≥0.80）  ← 防 uid 漂移
  │
  ├─ 第 2 级 特征码（按文件隔离）
  │    ├─ feat_path_index : (完整路径, 特征码)
  │    ├─ feat_name_index : (文件名, 特征码)
  │    └─ 都取不到 → None，绝不跨文件借
  │    └─ take_matching : 只认原文等值，无位置兜底
  │
  └─ 第 3 级 相似度（同 locator + 同文件 + ratio ≥ 0.92）
```

### 6.2 核心原则

> **宁可判不匹配，也不猜。**

判不匹配的代价是「一条译文进 unmatched，需人工处理」，可见、可修。
猜错的代价是「一条错误译文静默写进游戏文件」，不可见、污染扩散。

这两者代价不对称，因此任何「猜测」都必须被删除，而不是「加日志后保留」。

### 6.3 测试体系

新增 `tests/test_pipeline_no_misplacement.py`，18 用例 / 11 组场景：

| 场景 | 覆盖 |

## 7. 为什么至今仍不能说「完美解决」

诚实回答你的问题：**这个 bug 已经无法再以已知形态复发，但「完美」这个词我不能用。**

理由有四条：

### 7.1 「未知形态」必然存在

六轮里每一轮都认为「找到根因了」。第六轮找到的是**四个并行缺陷**，其中两个是我自己在修的过程中引入、又被测试抓出来的（#8、#9）。

一个连续六轮都能绕过验证的缺陷类别，其根本特征是**静默**。只要验收标准还有任何一处停留在「数量」而非「内容」，就还有藏身处。

### 7.2 仍有已知未修的同类缺陷

`pytran/migrate.py` 的 `_align_strings`：

```python
str_rows.get(s.source)   # 无唯一性检查、无位置守卫
```

这与 #5 属于同一类（strings 按原文/位置对齐且无守卫）。它没有在本轮修复范围内，因为尚未收到该路径的用户报告。**这是一个已知的、同类别的、未修复的缺陷。**

### 7.3 用户工作区仍处于污染状态

本次修复只阻止**再次发生**，不会自动回滚已写错的 28 条 strings 译文。

恢复路径（需用户确认，会改动游戏文件）：
1. 用 `bak/game/20261025-185049/` 覆盖游戏目录
2. 重新导入
3. 回到 20 条待翻译

### 7.4 行为变更需要人工适应

合并导入的「兜底命中」数量会**减少**：原文被人工改过的行不再自动继承，会进 unmatched。这是有意的，但会改变用户的操作预期 —— 需要一轮真实使用来确认没有引入新的不便。

> 六轮修复，五轮在换匹配键，一轮在稳定匹配键。
