# FEATURE：AI 校对（全文逐行复核，取代 V7 编号错配检测）

- 日期：2026-10-24
- 触发：用户实测「模型返回 JSON 的 `i` 编号错位 → 译文张冠李戴」，且明确裁决
  **「我需要能够 100% 判断错配的方法，而不是似是而非的方法。」**
- 前身：[`FEATURE-v7-mismatch.md`](FEATURE-v7-mismatch.md)（拟声词/长度倒挂/
  尖叫交叉启发式，**已全部删除**）
- 状态：✅ 已实现（`552 passed`）

## 1. 为什么放弃启发式

批次内部不存在能**验证**错配的信息。一批 30 行里，模型把编号整体平移一位后，
每条译文单独看都通顺、成批看也自洽——唯一能用的线索是「这条译文不像这条原文」，
而这只能**推断**，不能验证。于是：

- 判据写得松 → 漏报（平移一位型恰好每条译文只出现一次，重复判据抓不到）；
- 判据写得紧 → 误报（`Yes.` / `Sure.` / `Right.` 三条中文都译作「嗯。」，
  重复判据把它们全判错配；`咳咳咳！` / `哎呦喂！` / `呼……` 不在拟声字表里）。

**拟声字表是开放集**：补一个字就多一片误报区，永远补不完。用户拒绝这个方向。

## 2. 替代方案：全文逐行复核

把**全文**的「原文 / 译文」逐行发给模型，让它为**每一行**给出结论。

### 2.1 成本（用户 12062 已译段实测口径）

| 方案 | 折算倍数 | 请求数 | 结论 |
|---|---|---|---|
| 批次翻译（现状） | 1.00× | — | 基准 |
| **全文复核（本方案）** | **1.06×** | 201（60 行/块） | ✅ 采纳 |
| 逐行单发翻译 | 3.01×（无上下文）/ 5.63×（带 3 行上下文） | 12062 | ❌ 用户否掉 |
| 置换检验 | 2× | 2× | ❌ 上下文错乱反而降质 |

复核的**输入**成本几乎与窗口大小无关（≈ `N ×(原文+译文)`），窗口开大只是
请求数变少。真正的约束是**输出**预算（见 2.3）。

### 2.2 每行必须有回执（本设计的核心约束）

「模型什么都不报」是最大风险。因此提示词硬性要求：**每一个编号都要输出一行**，
`编号|ok` 或 `编号|NG|<一句中文说明>`。**没有回执的行 = 未确认**，单独归类
（「AI 校对（未确认）」），默认按需重译——绝不静默当作通过。

### 2.3 输出预算才是瓶颈

`uid|ok` 约 2.5 token/行。8192 输出预算下：

| 情况 | 可确认行数 |
|---|---|
| 无推理链 | ~3270 |
| R1 类推理模型消耗 800 token 思考 | ~2960 |
| 消耗 1500 token | ~2670 |
| 消耗 3000 token | ~2070 |

一旦截断，尾部行全部没有回执。故 `ReviewRunner` 带**窗口减半重发**：某窗口
未确认行占比 > 20% 即对半切开重发（最多 3 轮），仍无回执的进「未确认」。

### 2.4 窗口大小

131072 token 上下文 × 0.55 安全系数 = 72089 token 预算，实测 22.7 token/行：

| 窗口 | 实测输入 token | 占上下文 |
|---|---|---|
| 500 | 11442 | 8.7% |
| 1000 | 22811 | 17.4% |
| **2000（默认）** | **45400** | **34.7%** |
| 3000 | 68100 | 52.0% |

## 3. 交互（用户 2026-10-24 决策）

> 「AI 校对做成面板里单独的按钮」＋「并入同一张表，『重译』一起处理」

「全面审校」面板只跑**规则检查**（标签/转义/引号/英文/术语），秒出结果、
不花 token。底部提供独立的 **AI 校对** 按钮，由用户主动决定是否花 token：

```
┌─ 全面审校结果 ─────────────────────────────────┐
│ 共扫描 12062 段，命中 87 段 / 93 处问题。        │
│ ┌──────┬──────────────┬──────────────────────┐ │
│ │ 状态 │ 文件:uid     │ 问题                 │ │
│ │ 已译 │ a.rpy:14551… │ [标签] 缺少 {size}   │ │
│ │ 已译 │ a.rpy:14551… │ [AI 校对] 译文是别行 │ │
│ │ 已译 │ a.rpy:14551… │ [AI 校对（未确认）]… │ │
│ └──────┴──────────────┴──────────────────────┘ │
│ AI 校对完成：12062 行 / 7 个窗口；判 NG 12 行… │
│ [AI 校对]                            [重译]   │
└────────────────────────────────────────────────┘
```

- 双击任意行 → 定位到审校页对应段（规则问题与 AI 问题同一路径）；
- 「重译」→ 表里所有命中的段（两类一起）置 FAILED 回重译队列。

## 6. 已知边界（诚实声明）

1. **复核是推断，不是验证**。它把误判率压到远低于启发式，但不等于 100%。
   真正的 100% 只在**单行重译**那一层——一行一个请求，没有同伴可错位。
   复核的价值是：以 1.06× 的成本把「可疑行」缩小到极小集合，再对它付
   5.63× 的单行重译（12062 行里通常只有几十行，摊薄后约 0.14×）。
2. **自洽性偏差**：同一个模型复核自己的译文会偏宽松。设置里可换复核模型
   （默认 `deepseek-ai/DeepSeek-R1-0528-Qwen3-8B`）就是为了错开。
3. **短行/近似行**仍有残余漏报（`...` → `……` 这类判 ok 是合理的）。
4. **`review_max_tokens=8192` 是估算值**。131072 是
   `max_position_embeddings`，不是服务端 `max_tokens` 上限；硅基流动的实际
   上限本环境无法核实，请在设置里按实际值调整。
5. **引擎自动复核阶段尚未接入**：目前 AI 校对只在面板手动触发。
   `review_enabled` 字段已就位，接入后即为「翻译完成后自动复核 → 命中行
   单行重译」的两级流程。
